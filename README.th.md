# Alpha-Omega Trading

**_ชื่อรหัส "Denaro" — เอ็นจิน(grid-trading) แบบรวมศูนย์และกระจายสำหรับ OKX และ Kraken พร้อมกระดานซื้อขายจำลอง (paper trading) ที่สมจริง การเพิ่มเงินทุนสดแบบเป็นขั้น และการเฝ้าดูผ่าน Zabbix_**

Alpha-Omega trading เป็นระบบภาษา Python ที่รันเอ็นจินการซื้อขายเดียวกันบนเครื่องหลายเครื่อง ("โหนด") โดยแต่ละโหนดเทรดตลาดหนึ่งตลาดขึ้นไปบน OKX หรือ Kraken ผ่านไลบรารี CCXT ระบบนี้ออกแบบมาเพื่อการนำไปใช้อย่างมีระเบียบผ่านการ backtest และการตรวจสอบในโหมด paper trading โดยมี**งบประมาณเงินทุนสดที่จำกัดและเพิ่มขึ้นเป็นขั้น** — บัญชีเทรดจริงจะถูกแยกออกจากการพัฒนาโดยตั้งใจ และมีขนาดเล็กพอที่การขาดทุนเต็มบัญชีจะรับได้ในขณะที่เอ็นจินยังอยู่ในช่วงการตรวจสอบความถูกต้อง

## สถานะอย่างตรงไปตรงมา

นี่คือ**ซอฟต์แวร์ระดับงานวิจัยที่อยู่ในระหว่างการตรวจสอบด้วยการเทรดจริง** ไม่ใช่ผลิตภัณฑ์ที่เสร็จสมบูรณ์เพื่อทำกำไร

- การเทรดเกิดขึ้นจริงแต่ดำเนินการบน**งบประมาณเงินทุนจำนวนเล็กน้อย** (ระดับหลักสิบยูโร) โดยจำกัดขอบเขตไว้โดยตั้งใจเพื่อให้ข้อบกพร่องและการขาดทุนเป็นเรื่องที่รับได้ในระหว่างที่พิสูจน์ว่าเอ็นจินทำงานได้
- กลยุทธ์จะถูกตรวจสอบความถูกต้องก่อนใน**แพลตฟอร์มเทรดจำลอง (paper trading) ที่สมจริง**ก่อนที่จะจัดสรรเงินทุนสดใด ๆ และเงินลงทุนสดจะถูกเพิ่มขึ้นเป็น **ขั้น (stages)** ต่อเมื่อผ่านเกณฑ์ที่อิงตามสถิติเท่านั้น (ดู [แผนงาน](#แผนงาน))
- ความพยายามในอดีต**ไม่ได้ให้ผลลัพธ์ที่แข็งแกร่งอย่างสม่ำเสมอ** โค้ดเบสปัจจุบันสะท้อนบทเรียนจากความพยายามเหล่านั้น: การให้ความสำคัญกับ kill-switch, stop-loss, การตรวจสอบก่อนรัน (pre-flight checks) และการบันทึกค่าธรรมเนียม/ค่าสลิปเพจอย่างซื่อตรง แทนที่จะเป็นการคาดการณ์ในแง่ดี
- ไม่มีตัวเลขใดในที่เก็บนี้ที่เป็นสัญญาว่าจะได้ผลตอบแทนในอนาคต โปรดดู [ข้อจำกัดความรับผิด](#ข้อจำกัดความรับผิด)

โปรดถือว่าที่เก็บนี้เป็นข้อมูลอ้างอิงว่าควร**ทำอย่างไร**และ**ไม่ควรทำอย่างไร**เมื่อบริหารกองเรือซื้อขายอัลกอริทึมขนาดเล็ก — และจัดการความคาดหวังของตัวคุณเองตามนั้น

## ระบบนี้ทำอะไร

เอ็นจินรัน**การเทรดแบบ grid สองทาง**: วางคำสั่งซื้อเมื่อราคาร่วงต่ำลงไปตามบันไดระดับที่กำหนดไว้ล่วงหน้า และวางคำสั่งขายที่ระดับ take-profit ที่อยู่สูงกว่า โดยเก็บกำไรเล็ก ๆ จากการแกว่งตัวในขณะที่ถือครองสินค้าคงคลังระหว่างระดับเหล่านั้น กลยุทธ์หลายตระกูลอยู่ภายใต้ `denaro/domain/` (grid, momentum, mean-reversion, แบบ adaptive/volatility และแบบปรับตามสภาพตลาด (regime-aware)); เอ็นจินของโหนดที่อยู่รอบกลยุทธ์เหล่านี้เป็นเอ็นจินเดียวกันและไม่ขึ้นกับตัวแลกเปลี่ยน (exchange-agnostic)

ลักษณะสำคัญ:

- **เอ็นจินเดียว ตลาดมากมาย.** กระบวนการ `denaro.denaro_node` เดียวกัน ซึ่งกำหนดค่าผ่านไฟล์ YAML รันชุดค่าผสมใดก็ได้ของตลาดเทรดจริงและตลาด paper พร้อมงบประมาณต่อบอท สัญลักษณ์ ระดับ และการตั้งค่าความเสี่ยง
- **Paper trading ที่สมจริง.** เอ็นจิน paper เฉพาะทางนำค่าธรรมเนียมของตัวแลกเปลี่ยนจริง ขนาดขั้นต่ำของคำสั่ง (minimum notional) สลิปเพจ และ stop-loss มาใช้ เพื่อให้ผลลัพธ์ของการจำลองเปรียบเทียบได้กับพฤติกรรมในการเทรดจริง
- **ไม่ขึ้นกับตัวแลกเปลี่ยน.** การเข้าถึงคำสั่งและข้อมูลตลาดทั้งหมดอยู่หลังชั้น adapter (ซึ่งอิงกับ CCXT) ใน `denaro/infrastructure/exchanges` ดังนั้นกลยุทธ์จึงไม่ต้องพูดคุยกับตัวแลกเปลี่ยนรายใดโดยตรง
- **มุ่งเน้นประสิทธิภาพ.** I/O แบบอะซิงโครนัส ฟีดราคาผ่าน WebSocket พร้อมการกระจายข่าวผ่าน ZMQ การจำกัดอัตรา (rate limiting) และ supervisor ที่หน่วง tick ภายใต้แรงกดดันของ CPU/RAM

## สถาปัตยกรรม

กองเรือมีการกระจายไปยังเครื่องสามประเภทโดยแบ่งตามบทบาท ไม่ใช่ตามโทโพโลยีที่ตายตัว:

- **โหนดเทรด (Trading nodes)** — โฮสต์ VPS (โปรเจกต์นี้ใช้อยู่สองเครื่อง เรียกแทนด้วยคำว่าโหนด) ซึ่งรันกระบวนการ `denaro_node` หนึ่งกระบวนการขึ้นไป แต่ละกระบวนการอ่าน `config/node_*.yaml` ของตนเองและรายงานสถานะสุขภาพ
- **โฮสต์เฝ้าดู (Monitoring host)** — เครื่องที่รวบรวมสถานะสุขภาพของโหนดและทำหน้าที่เฝ้าดู ในการติดตั้งปัจจุบัน เครื่องนี้อยู่หลัง CGNAT และเข้าถึงได้ผ่าน **reverse SSH tunnel** ที่กำเนิดจากโหนดเทรดเท่านั้น จึงไม่จำเป็นต้องมีกฎ firewall ด้านขาเข้า
- **ชั้น orchestrator / ฟีดเดอร์ (ไม่บังคับ)** — เอ็นจินยังรวมชั้น "สมอง"/ฟีดเดอร์ที่ใช้ประสานการตัดสินใจระดับสูงและส่งต่อสัญญาณระหว่างส่วนประกอบ

มุมมองอย่างง่ายของความสัมพันธ์ในระหว่างการทำงาน:

```
┌──────────────┐   ┌──────────────┐     ┌──────────────┐
│   NODE A     │   │   NODE B     │     │  ORCHESTRATOR│
│ denaro_node  │   │ denaro_node  │     │ (optional)   │
│ grid markets │   │ grid markets │     │  brain/feed  │
└──────┬───────┘   └──────┬───────┘     └──────┬───────┘
       │                  │                    │
       └─────────┬────────┴────────────────────┘
                 │   health / metrics over network
        ┌────────▼─────────┐
        │   MONITORING     │   Zabbix server + web dashboard
        │   (aggregates,   │   reachable over reverse SSH tunnel
        │    https access) │
        └──────────────────┘
```

การสื่อสาร ระนาบควบคุม และรายละเอียดการเฝ้าดูขึ้นอยู่กับการติดตั้งแต่ละครั้ง กลไกที่ใช้ในปัจจุบันคือ **reverse SSH tunnel (autossh)** เพื่อให้เครื่องที่อยู่หลัง NAT ยังสามารถเข้าถึงได้และทำหน้าที่เป็นเซิร์ฟเวอร์เฝ้าดู

## การควบคุมความปลอดภัยและความเสี่ยง

การบริหารความเสี่ยงถือเป็นข้อกังวลระดับแรกที่ถูกฝังอยู่ในเอ็นจินของโหนด ไม่ใช่การติดตั้งเพิ่มภายหลังต่อกลยุทธ์แต่ละตัว:

- **Stop-loss** ต่อบอท พร้อมกับ**เซอร์กิตเบรกเกอร์รายวัน/รายสัปดาห์ทั่วทั้งระบบ (global)** ที่หยุดสัญลักษณ์หรือโหนดเมื่อข้ามขีดจำกัดการขาดทุนที่กำหนดไว้
- **การตรวจสอบก่อนรัน (pre-flight checks)** ก่อนการวางคำสั่งทุกรายการ (การตรวจสอบป้องกัน deadlock และการคำนวณขนาดสถานะ) เพื่อให้บอทที่ตั้งค่าไม่ถูกต้องหรือเก่าเกินไปไม่สามารถเทรดอย่างมืดบอดได้
- **โหมดปลอดภัย (safe mode)** — ชุดสถานะการบังคับให้ช้าลงแบบเป็นขั้น (caution → safe → emergency) ที่ขับเคลื่อนโดย supervisor (แรงกดดันจาก RAM/CPU/tick) ซึ่งจะค่อย ๆ ชะลอหรือหยุดโหนดก่อนที่ทรัพยากรจะหมด
- **บัญชีย่อย (Sub-accounts).** การเทรดจริงบน OKX/Kraken ดำเนินการบน**บัญชีย่อย**เฉพาะของตัวแลกเปลี่ยน ไม่เคยใช้บนบัญชีหลัก เพื่อให้ความผิดพลาดจากการปฏิบัติงานถูกจำกัดไว้ในขอบเขต
- **ข้อมูลประจำตัว** อยู่ในไฟล์ `.env` ในเครื่องเท่านั้น (ไม่มีวันถูก commit) และถูกโหลดตอนรันไทม์
- **การแบ่งงบเงินทุนสดเป็นขั้น.** เงินทุนถูกขยายเป็นขั้นอย่างชัดเจน (paper → เทรดจริงขนาดเล็ก → เทรดจริงขนาดใหญ่ขึ้น) และต่อเมื่อผ่านเกณฑ์ที่บันทึกไว้ในแผนงานเท่านั้น

## การเฝ้าดูและการแจ้งเตือน

- **Zabbix** ถูกใช้เป็นระบบรวมรวมข้อมูลและแจ้งเตือน โหนดส่งข้อมูลเมตริก (equity, PnL ต่อบอท, การบล็อกจาก pre-flight, สถานะสุขภาพที่เก่า, แรงกดดันทรัพยากร) ไปยัง **trapper** ของ Zabbix
- มีทริกเกอร์สำหรับ: การข้ามเซอร์กิตเบรกเกอร์, การขาดทุนรายวัน/รายสัปดาห์, หัวใจเต้นที่เก่าเกินไป (stale heartbeats), การบล็อกจาก pre-flight, แรงกดดันทรัพยากร
- **Auto-heal ถูกปิดใช้งานโดยค่าเริ่มต้น.** การทำซ้ำในยุคแรก ๆ รีสตาร์ทบอทเทรดจริงโดยไม่มีเหตุอันควร; การกู้คืนในปัจจุบันเป็นการกระทำที่ตั้งใจและมีการบันทึกไว้ แทนที่จะเป็นการรีสตาร์ทอัตโนมัติ
- **เว็บแดชบอร์ด**แบบอ่านอย่างเดียวให้มุมมองด่วนเกี่ยวกับสถานะสุขภาพของโหนดและบอท

## เริ่มต้นใช้งาน

ข้อกำหนด:

- Python **3.12+**
- สภาพแวดล้อม `uv` หรือ `venv`
- Docker + Docker Compose เฉพาะเมื่อคุณจะรันสแตกการเฝ้าดู Zabbix ด้วยเท่านั้น
- คีย์ API ของตัวแลกเปลี่ยนสำหรับ OKX และ/หรือ Kraken (ในไฟล์ `.env` ภายในเครื่อง ห้าม commit)

โคลนและติดตั้ง:

```bash
git clone git@github.com:grivetto/alpha-omega-trading.git
cd alpha-omega-trading

python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # then fill in your API keys
```

## การรันโหนดเทรดจริงและโหนด paper

เอ็นจินเป็นแอปพลิเคชันคอนโซลที่ขับเคลื่อนโดยไฟล์กำหนดค่า:

```bash
# Live grid node (per config file)
python -m denaro.denaro_node --config config/node.yaml

# Paper trading node
python -m denaro.denaro_node --config config/node_paper.yaml

# A Kraken trend-following live config (example)
python -m denaro.denaro_node --config config/node_trend_live_kraken.yaml
```

ไฟล์กำหนดค่าเพิ่มเติมที่ให้มา (`config/node_nuvola.yaml`, `config/node_mc2.yaml`, `config/node_adaptive_vol_grid_paper.yaml`, …) ตรงกับบทบาทเฉพาะของโหนด/กลยุทธ์ ดูส่วน [การกำหนดค่า](#การกำหนดค่า)

รัน `python -m denaro.denaro_node --help` เพื่อดูแฟลก (`--verbose` รองรับด้วย)

## การรันเป็นบริการ systemd

สำหรับโหนดในระบบผลิต มีไฟล์ unit ให้ภายใต้ `systemd/`. ขั้นตอนโดยทั่วไปบนโฮสต์หนึ่ง ๆ:

```bash
sudo cp systemd/*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now denaro-node            # name depends on the host role
```

ไฟล์ unit ในปัจจุบันครอบคลุมบทบาทโหนด, health, aggregator, dashboard, feeder และ reverse-tunnel (`zabbix-tunnel`) **ปรับแก้เส้นทาง `ExecStart`** ในไฟล์ unit ให้ตรงกับ home ของผู้ใช้ เส้นทางที่เก็บ และ venv ที่ใช้บนแต่ละโฮสต์ — ค่าที่ให้ไว้สะท้อนการติดตั้งแบบเฉพาะเจาะจงครั้งหนึ่ง

## การกำหนดค่า

โหนดแต่ละตัวอ่านไฟล์ YAML ที่กำหนด ระหว่างอื่น ๆ สิ่งต่อไปนี้:

- `exchange_rest`: ตัวแลกเปลี่ยน (เช่น `okx`) และโหมด EEA
- `bots`: รายการตลาด แต่ละตลาดมีสัญลักษณ์ `mode` (`live`/`paper`) `capital` ระดับ grid `levels` และการตั้งค่าเฉพาะกลยุทธ์
- `safemode`: เกณฑ์การบังคับให้ช้าลงของ RAM/CPU (`caution_pct`, `safe_pct`, `emergency_pct`) และช่วงเวลา (interval) ของเกณฑ์เหล่านี้
- `supervisor`: เกณฑ์สำคัญต่อทรัพยากรและการบังคับความถี่ของ tick
- `data_dir`: ที่ที่โหนดบันทึกสถานะรันไทม์และข้อมูลตลาด

ให้เก็บข้อมูลประจำตัวของตัวแลกเปลี่ยนให้พ้นจากไฟล์กำหนดค่า — ใส่ใน `.env` และโหลดที่รันไทม์

```
config/                  Per-node YAML configuration
denaro/
  domain/                Strategies and risk/regime/indicator logic (grid, momentum, adaptive, …)
  application/           Orchestration: portfolio, supervisor, safe-mode
  infrastructure/        Exchange adapters (CCXT), market data, storage, feeder
  denaro_node.py         Unified node entry point
scripts/                 Deployment helpers
systemd/                 systemd unit files (node, health, aggregator, tunnel, …)
zabbix/                  Monitoring integration (healer, push_metrics)
tests/                   Tests
.env.example             Credential template (keys never committed)
```

## ข้อจำกัดความรับผิด

**ซอฟต์แวร์นี้จัดทำขึ้นเพื่อวัตถุประสงค์ทางการศึกษาและการวิจัยเท่านั้น ไม่ใช่คำแนะนำทางการเงิน** การซื้อขายสินทรัพย์คริปโตแบบอัลกอริทึมมีความเสี่ยงอย่างมาก รวมถึงการสูญเสียเงินลงทุนทั้งหมด ผลการดำเนินงานในอดีตหรือในโหมด paper ไม่ได้รับประกันผลลัพธ์ในอนาคต; ค่าธรรมเนียม สลิปเพจ ช่องว่างสภาพคล่อง (liquidity gaps) และการหยุดทำงานของตัวแลกเปลี่ยน ล้วนสามารถเปลี่ยน backtest ที่ทำกำไรให้กลายเป็นแคมเปญเทรดจริงที่ขาดทุนได้ จงใช้เงินทุนที่คุณรับการสูญเปล่าได้ทั้งหมดเท่านั้น และไม่ควรเทรดด้วยเงินที่คุณพึ่งพา ผู้พัฒนาจะไม่รับผิดชอบต่อความสูญเสียใด ๆ ที่เกิดจากการใช้โค้ดนี้
