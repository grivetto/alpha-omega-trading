# Framework research: NautilusTrader vs OctoBot (as of 2026-09-23)

**[V]** = verified at cited URL. **[U]** = not verified (could not confirm) — not guessed.

## A. NautilusTrader (`nautechsystems/nautilus_trader`)

**1. Short/futures/venues/margin [V].** `OmsType.UNSPECIFIED|NETTING|HEDGING`; strategy/venue mismatch creates *virtual positions*; venue hedge mode needs adapter config (e.g. Binance Futures hedge mode) ([execution](https://nautilustrader.io/docs/latest/concepts/execution/)). Stable integrations: Binance, Bybit, OKX, Coinbase, Kraken, Deribit, Hyperliquid, dYdX, Derive, Lighter, AX, IB, Polymarket, Betfair, Databento, Tardis ([integrations](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/integrations/index.md)).

**2. Sandbox/paper — the key point [V].** `nautilus_trader.adapters.sandbox.SandboxExecutionClient` runs the same core: backtesting docs say simulation uses "the same core system components used in live trading: built-in engines, the `Cache`, the `MessageBus`, `Portfolio`, `Actors`, `Strategies`, `Execution Algorithms`"; the crate doc says it "provides a simulated execution client that uses the `OrderMatchingEngine` to simulate order execution against live market data. This enables paper trading and strategy testing in real-time without actual order execution on exchanges" ([docs.rs](https://docs.rs/nautilus-sandbox/latest/nautilus_sandbox/), [backtesting](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/index.md)). Config: `latency_model` (`StaticLatencyModel`, inbound leg only), `fee_model`, `fill_model`, `liquidity_consumption`, `queue_position`, `bar_execution`, `oms_type` ([API](https://nautilustrader.io/docs/python-api-nightly/adapters/sandbox.html)). Caveats [V]: "The simulated exchange does not interpret `close_position` or replace the placeholder with the open position quantity"; sandbox "generates no order status reports", so reconciliation is partly inert there.

**3. Lookahead/walk-forward [V].** Bar execution splits each bar into 4 synthetic L1 updates; `bar_adaptive_high_low_ordering` is a "deterministic heuristic, not a reconstruction"; `ts_init` must be the interval **close**; "Orders submitted from `on_bar` arrive only after all four points for that bar have been processed"; warning: "The engine does not provide a native next-bar-open fill mode… Using the current bar's open from its `on_bar` callback would introduce look-ahead." `add_data` "orders each stream by replay timestamp and merges all streams chronologically" ([bar execution](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/bar-execution.md), [execution flow](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/execution-flow.md), [apis](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/backtesting/apis-and-runs.md)). **[U]** No built-in walk-forward/optimizer — only `reset()`/`BacktestNode` repeated runs.

**4. Maturity [V].** Latest **v1.231.0, 2026-08-02** (final 1.x; `develop` → v2-only; v2 wheels 2.0.0rc, crates 0.64.0 dated 2026-09-15) ([release](https://github.com/nautechsystems/nautilus_trader/releases/tag/v1.231.0)); pushed 2026-09-23; 29,316 stars / 3,874 forks / 137 open issues; **LGPL-3.0**; company-backed (Nautech Systems) ([repo API](https://api.github.com/repos/nautechsystems/nautilus_trader)).

**5. Custom daily trend [V].** Python `Strategy` + `on_bar`, `BarType("…-1-DAY-LAST-EXTERNAL")`; trailing stops are native (`TRAILING_STOP_MARKET`/`TRAILING_STOP_LIMIT`, `trailing_offset` + `trailing_offset_type` `PRICE|BASIS_POINTS|TICKS|PRICE_TIER`); brackets/OTO/OCO; stops carry `trigger_price`/`trigger_type`/`reduce_only` ([orders](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/orders/index.md)). Channel breakout + EMA100 + ATR trail = plain `on_bar` code. **[U]** No documented built-in risk-per-trade sizer (sizing is user code).

**6. Porting [V].** Async ccxt loop → event callbacks (`on_start/on_bar/on_order_filled/on_position_changed`); typed values (`Price`, `Quantity`, `Money`, `ClientOrderId`); `instrument.make_price/make_qty` precision; daily `ts_init`=close. Adapters are native WS/REST clients, **not ccxt**.

**7. Decisive.**
(a) **[V]** `close_position(position)` forwards `position.id`; under NETTING the ID is deterministic `{instrument_id}-{strategy_id}`; the simulated exchange "cancels the order when the associated position becomes flat" and "reduces the order quantity as the associated position shrinks"; `reduce_only` blocks exposure increases; `full_position_exit_venues` allowlists venue-side whole-position exits.
(b) **[V]** Startup + continuous reconciliation against venue reports, `reconciliation_lookback_mins`, authoritative position reports "fail closed", synthetic terminal events (`INFLIGHT_TIMEOUT`, `NOT_FOUND_AT_VENUE`) ([reconciliation](https://nautilustrader.io/docs/latest/concepts/execution/reconciliation/), [policies](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/concepts/execution/policies.md)). **[U]** No documented automatic *re-placement* of a rejected stop.
(c) **[V]** `OrderFactory` "generates client order and initialization IDs when needed"; duplicate `trade_id` fills rejected, but "does not guarantee exactly-once delivery"; adapters retry only "when the venue protocol makes repetition safe, such as through stable request identity and duplicate detection". Documented **persistence gap** (order can reach venue before durable commit).
(d) **[V]** `OrderFilled`/`PARTIALLY_FILLED`, position aggregation, `position_id` assignment/override, `OrderFillVoided`.
(e) **[V]** `Cache` restores "accounts, orders, and positions" from Redis/Postgres; limits: unsupported with custom clients, rejected on a hosted event loop, async writes.

## B. OctoBot (`Drakkar-Software/OctoBot`)

**1. [V]** Binance/Bybit/KuCoin **spot + futures**, Hyperliquid/MEXC/Coinbase spot, "15+" via CCXT (README). Futures is fragile: [#3532](https://github.com/Drakkar-Software/OctoBot/issues/3532) KuCoin Futures chained SL/TP silently never created — "position left completely unprotected"; [#3536](https://github.com/Drakkar-Software/OctoBot/issues/3536) `NotImplementedError: Futures are not supported yet` and **"a short position gets closed when a long position is opened"**; [#3235](https://github.com/Drakkar-Software/OctoBot/issues/3235) OKX hedge mode "can't be traded", SL never triggered; [#3535](https://github.com/Drakkar-Software/OctoBot/issues/3535) futures needs market orders. Margin modes **[U]**.

**2. [V]** README advertises "risk-free paper trading" (simulator guide) and a built-in backtester *only in manual OctoBots*. **[U] The critical fidelity question is unverified**: octobot.cloud returned Cloudflare 403; no doc states the simulator swaps only the venue adapter while sharing the live OMS (the simulator is a separate connector: `exchange_simulator_connector.py`, `trader_simulator.py`).

**3. [V]** Built-in backtesting, a documented **Strategy Optimizer** ([deepwiki](https://deepwiki.com/Drakkar-Software/OctoBot/6.2-strategy-optimizer)), TradingView Pine Script signal automation, and `OctoBot-Script` 0.1.1 **alpha** (Python 3.13, asyncio, `obs.market(ctx,"buy",amount="10%",stop_loss_offset="-15%",take_profit_offset="25%")`) ([OctoBot-Script](https://github.com/Drakkar-Software/OctoBot-Script)). **[U]** Lookahead/walk-forward semantics.

**4. [V]** Latest **3.0.0-beta2, 2026-08-06**; pushed 2026-09-23; 6,605 stars / 1,275 forks / 168 open issues; **GPL-3.0-or-later**; company-backed (Drakkar Software). **`OctoBot-Tentacles` and `OctoBot-Trading` are archived** (last pushes 2026-02-03 / 2026-02-01) ([repo API](https://api.github.com/repos/Drakkar-Software/OctoBot)). Contributor count **[U]** (API rate limit).

**5–6. [V]** Custom strategies go via OctoBot-Script or custom tentacles; ccxt **is** the execution layer (OctoBot-Trading: "Library for connecting OctoBot with crypto exchange APIs using CCXT"). No documented channel/EMA/ATR-trail primitives.

**7.** Stop/exit logic lives in **tentacles (plugins) [V]**: "[Binance] add stop loss order" [#790](https://github.com/Drakkar-Software/OctoBot-Tentacles/pull/790), "[DipAnalyser] add stop losses" [#806](https://github.com/Drakkar-Software/OctoBot-Tentacles/pull/806), "[Exchanges] support spot stop losses" [#1396](https://github.com/Drakkar-Software/OctoBot-Tentacles/pull/1396), "skip stop losses on instantly filled orders" [#815](https://github.com/Drakkar-Software/OctoBot-Tentacles/pull/815), "handle take profit and stop loss on position increasing orders" [#948](https://github.com/Drakkar-Software/OctoBot-Tentacles/pull/948). Wrong-amount exit evidence: [#3536](https://github.com/Drakkar-Software/OctoBot/issues/3536). Restart reconciliation, idempotent client-order-ID reuse across retries, and a persisted Redis-style order/position ledger: **[U]** — none documented in reachable sources.

**Bottom line:** Nautilus answers (a)–(e) from primary docs/source with explicit limits; OctoBot only partially (a) via tentacles, and (b)/(c)/(e) are unverified with live futures-safety bugs open.
